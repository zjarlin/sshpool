# 架构和演进边界

控制面是一份 Rust 二进制。系统 OpenSSH 负责节点认证、HostKey、跳板和连接；TCP 透传层把客户端交给稳定 Linux 工作台的 OpenSSH。没有重写 SSH 协议，也没有为了统一入口改变原有设备路由。

## 一次构建

1. 项目必须有显式 `sshpool.toml`。客户端按路径稳定排序创建 tar，拒绝链接和常见凭据文件，并在写入前后比较文件清单以发现可见的并发修改。
2. 携带私有 token 和源码归档 SHA-256 上传到控制面。控制面限制上传数量、大小和时间，再次验证 tar 并独立重算摘要；不匹配时不发布任务。
3. 控制面对节点并行只读探测，在调度锁内做硬过滤：平台、CPU、内存、磁盘、负载、运行配额、未确认清理的任务，以及节点显式配置的**业务预算**（swap 用量 / 内存 PSI / IO PSI 上限——超预算或拿不到读数都拒绝接单）。排序在这之后看三样东西：显式 `priority`、这台机器跑同一类任务的实测完成时间、以及 CPU 余量与负载。实测来自已经落盘的尝试（同镜像、同命令、同平台、同资源申请，`exit 0`，起止时刻齐全），取最近窗口内最慢的一次；样本不足或旧记录没有收尾时刻就一律当作没有实测，退回静态排序。选中哪台、依据是什么会写进事件链的 `schedule` 事件 —— 没有历史的节点必须能看出「它是因为没数据而没有被优先」，而不是被当成最快。
4. 选择节点后先持久化任务与容器唯一标识，再通过系统 OpenSSH 创建受限容器。镜像必须已存在且在节点允许清单内，架构必须一致。镜像声明的 `VOLUME` 不是被拒绝，而是逐个用同路径、有上限的 tmpfs 遮蔽 —— 官方 Gradle 镜像就带一个缓存卷，直接挂匿名卷会让它绕开任务的内存与磁盘上限，而且没人清理。`VOLUME` 路径必须是绝对路径、不得超过 8 个，否则拒绝。容器创建后先按 `docker inspect` 的真实配置复核隔离、资源上限与卷遮蔽（`src/isolation.rs`），通过才 `docker start`；否则停在 `Created` 并删除。
5. 容器的 `/work` 和 `/tmp` 是有上限的 tmpfs，源码通过 stdin 导入；任务没有宿主目录挂载，`docker inspect` 的 `Mounts` 必须为空。根文件系统只读。`/work` 允许执行（编译产物要在里面运行），`/tmp` 禁止执行；两者都由创建后的真实配置复核。源码归档的成员 mtime 固定为 1980-01-01 而不是 1970：固定是为了归档可复算，而 1980 是 zip 能表达的最早时间，取 0 会让容器里的 `zipapp`、`jar` 之类直接失败。
6. 命令以非 root 身份执行；stdout/stderr 流回有大小上限的日志。超时或取消后核验标签并删除本任务容器。
7. 只收集声明的输出；控制面拒绝输出中的软硬链接、特殊文件和路径穿越。完整验证后发布产物。
8. 客户端在全新目录中提取产物；不会自动写回源工程。

## 故障语义

- 调度前资源不足：默认拒绝任务，保留每个候选节点的原因。任务可显式设置最长七天的持久等待期限和有限优先级；零等待保持原行为。
- 编译非零退出：失败，不重跑确定的编译错误。
- 基础设施错误/超时：只有任务明确幂等、禁网、配置重试、旧容器确认删除时才尝试下一节点。
- SSH 断线且清理无法确认：记录 `interrupted`，隔离该 Worker，拒绝进一步给它分配任务。隔离不要求重启控制面：`sshpool node reconcile [name]` 依据三类证据在线解除 —— 容器不存在、容器已停止，或 SSH 仍不可达但容器自带租约（`sleep 超时 + 180s`）已过期并留出 60 秒时钟偏差。证据写入 attempt 的 `cleanup_proof`；容器实际仍在运行时，即使租约已过期也拒绝放行。
- 控制面重启：读取原子替换的状态文件，核对并终止遗留容器；仅恢复未领取、原绝对期限未过且源码归档仍合法的队列请求，不重放已运行任务。
- 控制面消失：容器 PID 1 的限时进程终止后容器结束；停止的容器元数据由下次核对清理。
- 重跑只换机器：判据是该 Worker 出现过 attempt，**不按 `outcome` 过滤** —— 控制面在容器仍运行时崩溃会留下 `outcome: null`，那台机器同样执行过本次任务。重跑不增加额度，也不会回到旧机器。
- 客户端断线：任务仍由控制面管理，可以用任务 ID 重新查看日志和结果。

任务结果和源码归档存储在控制面本地磁盘，任务记录同时保存源码归档摘要。配置远端副本后，每个状态转换先写本地提交回执，再向不同物理故障域推送内容寻址归档，至少取得一台远端确认后才发布本地终态。quorum 2 表示本地加任意一台远端；配置两台远端时，任意一台远端故障仍可继续提交。恢复方会核对任务元数据、源码摘要和远端提交证明，冲突或不可读的新版本一律失败关闭。

远端副本只保护已确认的任务状态、源码、日志、事件和声明产物。运行中的进程、内存和尚未检查点的实时输出不会迁移。控制面也不会自动在另一台机器监听同一 SSH 地址：M3 丢失后，运维必须先用独立保存的配置、token 和 SSH 凭据重建控制器，并确保旧控制器已停止。完整故障矩阵见 [failure-modes.md](failure-modes.md)。

任务状态复制不保护 PostgreSQL、Redis、业务容器的可变目录或数据库事务。它们需要各自的备份、复制、写入隔离和故障注入验收；Ceph 健康、容器自动重启或任务元数据副本都不能替代这些工作。

节点可由管理员在线改设置，不需要重启控制面：接单状态、并发槽位、内存/磁盘预留、负载上限、优先级，以及业务预算的三项门槛。运行时节点视图是控制面里唯一权威的节点列表，探测、`/v1/status`、指标和调度都读它，所以一次更新对所有读取方同时生效。

写入顺序固定为「校验 → 原子落盘 → 替换内存 → 唤醒队列」，全部在调度锁内完成；因此不存在任务按半套设置被派发的中间态，也不会出现「内存改了、磁盘没改」这类重启后才自愈的偏差。落盘前会重新读一次 `config.toml` 并与内存逐字段比对：控制面运行期间有人手改了配置，在线更新会拒绝并提示重启加载，而不是把他的手改整份覆盖掉。

补丁只覆盖显式给出的字段，取消一项门槛要用 `clear`（CLI 的 `--clear-slo`），否则「没提到」与「取消」无法区分。`ssh` 与 `images` 不在补丁范围内：换目标等于换了一台机器（需重启核对 HostKey），授权镜像必须经 `node prepare` 真实拉取，混进一次在线补丁会让它同时承担两种风险。

镜像授权也免重启，但它是独立路由 `POST /v1/nodes/{name}/prepare`，语义是「拉取 + 授权」而不是「改列表字段」。顺序固定为「`docker pull` 成功 → 校验整份配置 → 原子落盘 → 替换内存 → 唤醒队列」：拉不到就不改配置，不会留下「已授权但机器上没有」的镜像。`docker pull` 是幂等且不碰配置的远端动作，放在调度锁外执行（大镜像可能拉几分钟，持锁会让所有派发停住），锁内重读 `config.toml` 与内存比对后再落盘；并发 `prepare` 与在线改设置因此不会互相覆盖。已有活动任务的节点不能被禁用。

撤销是 prepare 的反向路由 `POST /v1/nodes/{name}/revoke`，请求体同为 `{"image": "..."}`，语义是「只收缩允许清单」，不是「改一个列表字段」。它没有远端动作（不 `docker rmi`、不杀容器），所以整段在调度锁内完成，写入顺序与 `update_node` 相同：校验镜像名 → 比对 `config.toml` 与内存 → 保留式重建 `images` → 校验整份配置 → 原子落盘 → 替换内存 → 唤醒队列。撤销一张正由本节点活动任务执行的镜像会被拒绝并给出 job id：撤销不会停止容器，否则会留下「容器在跑、授权已消失」的错位，而这种错位只有在事后看任务记录才会被发现。清单里本来没有这张镜像时返回 `revoked=false`，不写盘也不产生伪变更。

## 信任和隔离

这是面向同一拥有者设备的单用户计算池。配置、token、SSH 运维账号和容器运行时属于可信控制边界；持有 token 的人可以请求资源范围内的构建。任务进程没有 Docker socket，也没有控制面的 SSH 凭据。

控制面默认只监听宿主回环的明文 HTTP。跨不可信网络时由 `src/tls.rs` 用 rustls 终止 TLS，客户端必须校验服务端证书（系统信任链或显式 `--ca-file`，没有跳过校验的开关）。需要把控制面借给工作台或临时脚本时，用 `src/credentials.rs` 签发短期凭据：磁盘只存 SHA-256 摘要，到期是半开区间，撤销后下一次请求即被拒绝。凭据库损坏时动态凭据一律拒绝，但根 token 仍然可用 —— 一个坏文件不该把运维锁在控制面之外。

短期凭据**按主体分级授权**：`Scope` 是五项白名单 `read` / `submit` / `cancel` / `admin` / `scrape`，签发时不写 `scopes` 只得 `read`。每份凭据至少要有一个入口：`read`（API）或 `scrape`（指标），两者都没有的记录（例如只有 `admin`）会让整份库拒绝加载；带任何 API 动作时会自动补 `read`，只写 `scrape` 时刻意不补。`Principal::require(scope)` 在各处理器入口做判断，越权返回 403 且只说明缺哪一项（``credential lacks the `admin` scope``）；401 仍是「身份不成立」，403 是「身份成立但越权」，两者都记 `decision=denied`，`status` 保留真实状态码。没有 `scopes` 字段的旧记录按最小权限降级为只读 —— 权限收紧宁可让旧脚本报 403，也不做「缺字段等于全部权限」的兼容。根 token 是运维凭据，四项全有。

动作权限之外还有**主体范围**：`Job.owner` 记录提交者主体名，由服务端按鉴权结果写入，客户端无法伪造。`Principal::owns` 判定「根 token，或带 `admin` 的运维凭据 → 全通；其余凭据 → 仅 `owner == subject`」。列表按主体过滤，单任务、日志、事件、产物的读取统一走 `readable_job`，取消在改写状态之前先过属主检查，所以被拒的请求不会留下 `cancel_requested`。越权返回 403 `credential does not own this job`，不用 404：404 会让「任务不存在」和「不属于你」混成同一个结论，排查时无法区分。错误体不包含属主名，避免凭据通过错误文本枚举别人的主体名。归属按主体名而非凭据 id 计算 —— 换一把新 token 仍能看到自己的历史任务，这也是为什么 `root` 被列为保留主体名。旧记录的 `owner` 为 `None` 表示归属未知，按 fail-closed 处理：只有运维主体能读。

`src/access.rs` + `src/api.rs::audit_access` 给每个请求留一行审计到 `home/access.jsonl`：主体、身份来源、凭据 id、决定与理由、方法、路由模板、任务 id、状态码。鉴权与留痕在同一个中间件里完成，处理器只拿 `Principal`，所以不存在"某个接口忘了记"。日志故意不含 token、请求正文和查询串，未命中路由只记 `unmatched` 而不记原始路径。文件按 4 MiB × 3 代滚动（上限 12 MiB），中间行损坏 fail-closed，只有当前文件末尾的崩溃半行被容忍并在下一次写入前切掉；审计不可写时副作用请求直接 503，不做没有记录的动作。

`src/placement.rs` 对一份拓扑描述做副本放置核算：同一物理机上的多个 VM 合并为一个故障域，物理盘与 VM 盘同域时拒绝（否则容量重复计算），可写容量按「副本落在不同域、每域对同一份数据最多一份」求上限，先扣恢复预留再报数。任何一项不成立就返回退出码 2，且把可用容量写成 0；它只做算术，不探测设备、不创建 OSD，也不证明耐久性。

`src/metrics.rs` 把控制面已有的结构化事实渲染成 Prometheus 文本：终态任务按 `phase` + `exit_code` 分成 6 类（成功、三种失败结构、取消、中断），排队与执行时长是累计桶直方图，另有尝试/重试计数、队列深度与最老等待、清理未确认数、节点资源水位，以及访问审计各代字节数。失败分类不解析 `job.message`，所以改文案不会改变语义；节点探测失败时资源报 0 而不是沿用旧快照，避免把陈旧数字读成当前水位。

指标走独立的 `metrics_listen`（默认关闭，启动行打印 `metrics=off` 或实际地址），不挂在 `/v1/...` 上：Prometheus 默认 15 秒抓一次，走控制面路由会经 `audit_access` 在几分钟内冲掉 12 MiB 的有界审计。抓取只读 `health_snapshot` 缓存，不触发远端探测。抓取要求**根 token**（`Bearer`，恒时比较，与 API 共用 `src/token.rs`）或一条带 `scrape` 的短期凭据（走 `credentials::verify`，因此撤销与到期在下一次抓取生效）；两者都不匹配一律 401 且不输出样本，配置 TLS 时该端口共用同一份证书。权限是**两个方向都隔离**的：带 `read` / `submit` / `cancel` / `admin` 的 API 凭据抓不到指标，`scrape` 凭据也没有任何 `/v1/...` 路由 —— 前者防止借出的工作台顺带看到集群拓扑，后者让 Prometheus 不必持运维全权 token。抓取不写访问审计，所以「谁抓过」不在 `access.jsonl` 里。默认只允许绑回环地址，跨主机抓取要显式 `metrics_allow_remote = true` 且必须配 TLS。暴露的仍只有节点名与数值。

`src/migration.rs` 把「迁移成功」变成可比较的判断：PostgreSQL 每张表的行数与行内容摘要、每个序列的 `last_value`，Redis 每个键的类型、规范化值摘要与精确绝对过期毫秒，两侧统一按名字排序后逐项比对；解析任何一行不合约定就失败关闭。它同时提供链式操作日志（`hash` 覆盖序号、时刻、步骤、详情与前一条摘要），可以在迁移进程退出后离线复核顺序与内容。模块只做判定与记录，数据层编排在 `tests/migration_live.rs`，真实应用编排由 `tests/sub2api_migration_live.rs` 调用 `scripts/sub2api-migration/rehearse.py`，共用同一份 SQL 与 Lua。应用演练记录共同比较时刻，仅排除已确定到期的 Redis 键，并独立复核旧写入方持续冻结。见 [验证记录](validation.md#stateful-migration)。

`src/state_audit.rs` 把「这个应用依赖哪些状态」变成可核对的输入：人写清单，`PROBE_SCRIPT` 只读地取容器、表、唯一索引、AOF/`appendfsync`、挂载设备号与用量，`assess` 是纯函数判定。三处刻意的取舍：备份只有三态枚举，人工备份的 RPO 就是 `None`（无上界），不会退化成 0 或某个大数；声明 Redis 只是缓存但探到无 TTL 键，则拒绝该声明并按权威状态计 RPO；声明与事实冲突时降级声明，而不是调整数字凑通过。宿主绝对路径只以摘要进报告。它不迁移、不备份、不改配置，`0` 只表示清单被核对过。见 [验证记录](validation.md#state-audit)。

Docker 容器共享内核，不能用此原型承诺对恶意租户的强隔离。公司重要主机建议使用专用计算 VM 或 rootless Docker，并持续更新运行时。宿主业务的突发负载仍可能影响任务，需要实测预留量。

工作台用户本身能编辑自己的工作台文件；任务容器只能看到显式提交的源码。两种权限不要混淆。构建时不要让源码同步工具并发更改项目文件。

## 对开源方案的取舍

- **OpenSSH**：承担完整 SSH 兼容性。Rust 只进行字节透传和节点命令编排。
- **Lima**：可选的 Mac Linux 工作台，关闭宿主目录共享；任何稳定 Linux/OpenSSH 后端也可替代。
- **Docker / Linux cgroups**：承担进程、资源和文件系统隔离。使用非 root、只读系统层、禁网与 tmpfs。
- **Slurm**：借鉴其资源预约和作业状态模型；首版没有引入集群身份数据库与守护进程部署。
- **sccache / Icecream**：后续适配编译单元调度与缓存。当前只分发整个命令，不能标成已集成这两者。
- **OpenSSI / Kerrighed / Popcorn**：记录为研究路线，不把实验内核混入公司主机，也不声称已有分布式共享内存。

## 后续工作

优先补上更细的分权（主体范围已按「只能操作自己提交的任务」落地，指标也有可单独撤销的 `scrape` 凭据，但还没有按节点、按项目分权，`scrape` 也是全有或全无、不能按节点过滤）、可配置输出导入策略、内容寻址输入缓存、sccache adapter、原生 macOS VM Worker，以及容器引擎内部资源探测。阶段事件已可按任务 ID 查询，指标已在独立端口上提供抓取；有限持久队列不等于控制面多实例高可用，服务多实例调度和真正的 SSI 属于独立能力，需要独立验收。
