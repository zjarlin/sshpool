# 故障与数据恢复边界

这份矩阵区分“可以丢失的运行资源”和“必须恢复的持久数据”。当前已完成的是任务状态跨物理故障域复制；进程迁移、自动控制面漂移和数据库高可用仍是不同能力。

## 完成任务状态保护后的保证

生产建议配置两个独立物理副本并设置 `replica_min_ack = 2`。quorum 2 表示本地控制面加任意一台远端确认。每份成功状态包含任务元数据、源码快照、日志、事件、声明产物和绑定本次提交的回执。

| 故障 | 服务与运行状态 | 持久任务数据 | 自动行为 |
| --- | --- | --- | --- |
| 任意一台 Worker 宕机 | 该机上的进程、内存、容器和临时文件丢失 | 已确认 checkpoint 由其他故障域保留 | 清理无法证明时任务进入 `interrupted` 并隔离 Worker；`sshpool node reconcile` 凭容器租约或远端状态解除隔离，仍运行则继续拒绝 |
| 一台远端状态副本宕机 | 正常提交仍可通过另一台远端达到 quorum 2 | 存活副本保留最近已确认版本 | 控制面继续；启动和恢复仍核对独立故障域 |
| 控制面主机宕机 | API、SSH 入口以及本机运行中的任务失去 | 任一远端副本可证明原控制面已经参与的最近提交 | 需人工在恢复机提供配置、token、SSH 凭据并启动；原控制器必须先停止 |
| 两台远端同时不可用 | 无法确认新的持久提交 | 本地已有文件不自动删除 | 控制器拒绝以 quorum 状态启动 |
| 控制面加其唯一远端故障 | 无法继续服务 | 仅在另一独立故障域持有提交时可恢复 | 没有 quorum 时失败关闭 |
| 站点全部三台物理机丢失 | 运行状态与本地数据全部丢失 | 本方案没有异地灾难恢复 | 需要预先配置站外备份 |

## 不能被当成“已经保存”的内容

- 正在运行的进程、内存、打开文件、网络连接和未提交的应用状态。
- 两次 checkpoint 之间写入的实时日志与事件；最近一次持久 checkpoint 之后的字节可能丢失。
- 控制面运行后的本地产物若尚未完成终态 quorum，可能只剩本机副本。
- 控制器 token、SSH 私钥、known_hosts 和工作台文件不进入任务状态归档，必须独立备份。
- 「证明旧容器终止」不等于「中断前的输出有效」；看门狗证据只排除并发提交，不恢复内存或进程。
- PostgreSQL、Redis、`sub2api` 可变目录、业务卷以及它们之间的事务边界不在任务状态复制内。

## 调度依据

「预计完成时间」只来自控制面自己观察到的完成：同镜像、同命令、同平台、同资源申请，`exit 0`，且 `started_at` 与 `finished_at` 都齐全。它不是清单声明，也不是对本次任务的预测。

- 少于 3 条样本 → 没有预期，退回 CPU 余量与负载排序。
- 旧记录缺 `finished_at` → 同样算「没测过」。按 0 补齐会把「没有测量」变成「立刻完成」，是这次刻意堵掉的漏洞。
- 失败的尝试不计入。3 秒就 `exit 1` 的机器不是「快」，是「坏了」。
- 取窗口内最慢一次而不是均值。问题问的是「这单最慢要等多久」，均值会把冷启动和缺缓存摊平成一个没发生过的数字。
- `priority` 仍排在实测前面：它是运维写下的意图，不是可以靠样本数量推翻的估计。
- 硬过滤永远在前。实测最快但槽位已满、内存不足、平台不匹配或处于隔离的节点，照样不能被选中。

## 业务预算

预算是**拒绝接单的条件**，不是健康评分。三件事要说清，否则它会被当成「业务 SLO 已达标」的证据：

- 只有三项有读数：swap 用量、内存 PSI、IO PSI。磁盘水位走的是既有的 `reserve_disk_mib`（可用空间下限），语义相同就不另设一套门槛。业务延迟与错误率没有实现——那需要业务侧埋点，本仓库没有定义业务流量，凭空写个阈值只会掩盖问题。
- **缺测量按超预算处理。** 没开 PSI 的内核、没有 swap 的平台、探测失败的节点，三项都是 `None`；配了门槛就是拒单。把「读不到」当成「很健康」是最容易发生、也最难发现的失效。
- 预算是硬过滤，排在排序之前。跑得最快、`priority` 最高的节点超预算照样出局；反过来，一台节点超预算不会让整池停摆，其他节点仍接单。

读数之间的含义不同，不要互相替代：swap 用量是**历史堆积**（`okm182` 上已用 32 GiB 而内存 PSI 仍是 0，说明曾经被换出过、此刻却没有任务在等内存），PSI 的 `some avg10` 是**此刻**有多少时间至少一个任务在等资源。要表达「业务正在被挤压就停」，配 PSI，不要配 swap。

还有一个它不是的东西：**只读采样不是压测**。探测不会为了判断预算去制造峰值负载，所以它保证的是「已经超预算时不再加码」，而不是「所有峰值下 SLO 达标」。想证明后者，只能在业务主机上做并发压力矩阵，那不在本仓库的自动化范围内。

## 节点设置的在线变更

`node update` 改的是**调度依据**，不是任务数据：不触碰已经领取的任务、容器与产物，也不重放任何东西。它的持久化边界比任务状态窄 —— 配置是控制面本机的一个文件，没有跨主机副本。

| 情形 | 结果 | 为什么这样选 |
| --- | --- | --- |
| 落盘成功、替换内存前进程崩溃 | 重启后读到新配置，与在线结论一致 | 顺序是「落盘 → 换内存」，反过来的话崩溃会丢掉刚改的值，还会让在线结论与磁盘分叉 |
| 落盘失败 | 内存保持旧值，请求报错 | 没有「先生效、稍后补写」：那会让运维以为改成功了，重启后又变回去 |
| 运行期间外部手改了 `config.toml` | 在线更新被拒绝，提示重启加载 | 控制面持有内存权威视图；静默整份覆盖会把运维的手改丢掉 |
| 更新与任务派发并发 | 派发看到的是旧值或新值，不会是半套 | 两者共用 `scheduling` 锁，节点视图的替换是整份的 |
| 禁用一个仍持有活动任务的节点 | 拒绝 | 那份容器会失去归属，清理确认也无从谈起 |

镜像授权是另一条路由（`POST /v1/nodes/{name}/prepare`），因为它要让远端产生副作用：

| 情形 | 结果 | 为什么这样选 |
| --- | --- | --- |
| `docker pull` 失败（镜像名错、仓库不可达、超时） | 配置与内存都不变，请求报错 | 反过来「先授权再拉取」会留下「已批准但机器上没有」的镜像，任务要到派发时才失败 |
| 同一张镜像重复准备 | 直接返回 `pulled=false`，不重复拉取、不写盘 | 它是幂等的「确保可用」，不是每次都要消耗带宽 |
| 拉取期间有人在线改了别的字段 | 锁内以最新内存值重建，不覆盖对方的改动 | 落盘的应当是两个动作的合并结果，而不是拉取前那份快照 |
| 运行期间外部手改了 `config.toml` | 检测在拉取之前，直接拒绝 | 明知配置已被别人改过还去拉镜像，等于在错误前提下产生远端副作用 |
| 控制面没在跑时执行 `node prepare` | 走离线路径（由 `controller.lock` 证明无控制面） | 首次部署必须在 `serve` 之前准备镜像；锁拿不到就走 API，不让一次失败的探测变成写配置的许可 |

撤销是第三条在线路由（`POST /v1/nodes/{name}/revoke`），只收缩允许清单，没有远端动作：

| 情形 | 结果 | 为什么这样选 |
| --- | --- | --- |
| 撤销一张正由本节点活动任务执行的镜像 | 拒绝，错误里带 job id | 撤销不 `docker rmi`、不杀容器；放任会留下「容器在跑、授权已消失」，只在事后看记录才会发现 |
| 同一张镜像重复撤销 | `revoked=false`，不写盘 | 幂等：没有可删的授权就不该产生一次磁盘写入 |
| 撤销从未授权过的 tag | `revoked=false`，`config.toml` 一字未变 | 同上；也不把「打错 tag」当成「已经撤销」 |
| 运行期间外部手改了 `config.toml` | 写入前检测，直接拒绝 | 与 `prepare`/`update` 共用同一条判定，不整份覆盖别人的手改 |
| 撤销之后重启控制面 | 读到撤销后的清单，结论不变 | 撤销先落盘再换内存，顺序与其它在线写一致 |

它**不是**热加载：外部修改 `config.toml` 不会自动生效。新增节点与全局配置（`max_active_jobs`、上传/产物上限、副本 quorum、TLS 路径）仍然要重启。`ssh` 与 `images` 也刻意不在补丁范围内 —— 换目标等于换了一台机器，必须有重新核对 HostKey 的时机；镜像则必须真的在机器上存在，不能靠改一行配置宣称可用。

## PostgreSQL 与 Redis

截止 2026-11-07，实际服务的 PostgreSQL `archive_mode=off`，Redis 使用 AOF，数据目录仍位于同一台物理主机和同一磁盘。单个逻辑备份能恢复某个时间点，但会产生从备份时间到故障时间的 RPO；存在旧备份也不能证明当前数据完整。

声明与事实冲突时**降级声明**，不要改数字凑通过。典型例子：Redis 被写成「可丢弃缓存」，但 `INFO keyspace` 里 `keys - expires` 有几千个键，那它承担的就是权威状态，RPO 必须按 AOF 配置算，而不能继续按 0 算；「说不清多久备份一次」既不是 0 也不是 86400，而是没有上界 —— 只有三态 `scheduled{interval}` / `manual` / `none` 的清单里，后两者都推出 `None`。`sshpool state-audit` 把这三条写成可执行判定，见 [应用状态与持久化约定审核](state-audit.md)。

**定时备份的声明本身不是证据。** 清单写 `scheduled` 只是提出主张：主机上必须有一个能唯一指认的 crontab 行 / `cron.d` 行 / systemd timer 对得上 `evidence`，否则按「没有定时备份」计 RPO。反过来同样要防：`crontab:root` 里通常挂着 `sysstat` 这类每 10 分钟一次的琐事，如果「来源对上就算数」，任意清单都能凭空拿到「RPO ≤ 10 分钟」。所以命中多条时判 `backup_schedule_ambiguous`，必须补 `#<命令摘要>` 精确指向其中一条；周期一律以观测值为准，解析不出来就是无上界。这类「自己给自己发合格证」的写法，比写错一个数字更难被发现。

数据库达到“确认事务不丢”至少需要：

1. 定期 PostgreSQL 基础备份，并持续归档 WAL 到独立物理故障域。
2. Redis 明确使用 AOF 或快照，核对 `appendfsync`，并复制实际持久文件。
3. `sub2api` 的可变目录与数据库写入形成同一恢复顺序；不能只恢复其中一侧。
4. 故障时先隔离旧写入方，再提升后备实例，避免双向写入。
5. 在独立演示数据上注入应用、数据库、网络和整机故障，记录并验收 RPO/RTO。

分层进度（不要跨层宣称）：**同一停写窗口内的数据层迁移与切回已在演示数据上验收** —— 两侧内容级指纹逐项相等、隔离期间应用用户写不进去、切回后旧写入方可重新写入且目标侧保持冻结（见 [验证记录](validation.md#stateful-migration)）。仍然**没有**验收的是：真实 `sub2api` 容器参与、入口层流量切换、停写窗口之外的增量、自动故障转移。所以「能迁移演示数据」不等于「生产数据库可以故障切换」。

## 存储

无 RAID 的多磁盘冗余不能把同一 ESXi 宿主上的多个 VM 当作独立容灾域。Ceph 等系统只能在其 OSD、网络、仲裁、快照或复制策略完成配置并通过故障注入后才提供存储冗余；存储健康也不自动等于数据库事务一致。

`.52` 在重装 ESXi 前必须保持禁用。重装后先只读确认专用磁盘、硬件身份和共享故障域，再决定是否加入；既有未知文件系统不得因为“即将重装”而被自动格式化或接管。
