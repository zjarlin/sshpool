# 故障与数据恢复边界

这份矩阵区分“可以丢失的运行资源”和“必须恢复的持久数据”。当前已完成的是任务状态跨物理故障域复制；进程迁移、自动控制面漂移和数据库高可用仍是不同能力。

## 完成任务状态保护后的保证

生产建议配置两个独立物理副本并设置 `replica_min_ack = 2`。quorum 2 表示本地控制面加任意一台远端确认。每份成功状态包含任务元数据、源码快照、日志、事件、声明产物和绑定本次提交的回执。

| 故障 | 服务与运行状态 | 持久任务数据 | 自动行为 |
| --- | --- | --- | --- |
| 任意一台 Worker 宕机 | 该机上的进程、内存、容器和临时文件丢失 | 已确认 checkpoint 由其他故障域保留 | 清理无法证明时任务进入 `interrupted` 并隔离 Worker；`sshpool node reconcile` 凭容器租约或远端状态解除隔离，仍运行则继续拒绝 |
| 一台远端状态副本宕机 | 正常提交仍可通过另一台远端达到 quorum 2 | 存活副本保留最近已确认版本 | 控制面继续；启动和恢复仍核对独立故障域 |
| 控制面主机宕机 | API、SSH 入口以及本机运行中的任务失去 | 任一远端副本可证明原控制面已经参与的最近提交 | 需人工在恢复机提供配置、token、SSH 凭据并启动；原控制器必须先停止 |
| 两台远端同时不可用 | 无法确认新的持久提交 | 本地已有文件不自动删除 | 控制器拒绝以 quorum 状态启动 |
| 控制面加其唯一远端故障 | 无法继续服务 | 仅在另一独立故障域持有提交时可恢复 | 没有 quorum 时失败关闭 |
| 站点全部三台物理机丢失 | 运行状态与本地数据全部丢失 | 本方案没有异地灾难恢复 | 需要预先配置站外备份 |

## 不能被当成“已经保存”的内容

- 正在运行的进程、内存、打开文件、网络连接和未提交的应用状态。
- 两次 checkpoint 之间写入的实时日志与事件；最近一次持久 checkpoint 之后的字节可能丢失。
- 控制面运行后的本地产物若尚未完成终态 quorum，可能只剩本机副本。
- 控制器 token、SSH 私钥、known_hosts 和工作台文件不进入任务状态归档，必须独立备份。
- 「证明旧容器终止」不等于「中断前的输出有效」；看门狗证据只排除并发提交，不恢复内存或进程。
- PostgreSQL、Redis、`sub2api` 可变目录、业务卷以及它们之间的事务边界不在任务状态复制内。

## PostgreSQL 与 Redis

截止 2026-11-07，实际服务的 PostgreSQL `archive_mode=off`，Redis 使用 AOF，数据目录仍位于同一台物理主机和同一磁盘。单个逻辑备份能恢复某个时间点，但会产生从备份时间到故障时间的 RPO；存在旧备份也不能证明当前数据完整。

声明与事实冲突时**降级声明**，不要改数字凑通过。典型例子：Redis 被写成「可丢弃缓存」，但 `INFO keyspace` 里 `keys - expires` 有几千个键，那它承担的就是权威状态，RPO 必须按 AOF 配置算，而不能继续按 0 算；「说不清多久备份一次」既不是 0 也不是 86400，而是没有上界 —— 只有三态 `scheduled{interval}` / `manual` / `none` 的清单里，后两者都推出 `None`。`sshpool state-audit` 把这三条写成可执行判定，见 [应用状态与持久化约定审核](state-audit.md)。

**定时备份的声明本身不是证据。** 清单写 `scheduled` 只是提出主张：主机上必须有一个能唯一指认的 crontab 行 / `cron.d` 行 / systemd timer 对得上 `evidence`，否则按「没有定时备份」计 RPO。反过来同样要防：`crontab:root` 里通常挂着 `sysstat` 这类每 10 分钟一次的琐事，如果「来源对上就算数」，任意清单都能凭空拿到「RPO ≤ 10 分钟」。所以命中多条时判 `backup_schedule_ambiguous`，必须补 `#<命令摘要>` 精确指向其中一条；周期一律以观测值为准，解析不出来就是无上界。这类「自己给自己发合格证」的写法，比写错一个数字更难被发现。

数据库达到“确认事务不丢”至少需要：

1. 定期 PostgreSQL 基础备份，并持续归档 WAL 到独立物理故障域。
2. Redis 明确使用 AOF 或快照，核对 `appendfsync`，并复制实际持久文件。
3. `sub2api` 的可变目录与数据库写入形成同一恢复顺序；不能只恢复其中一侧。
4. 故障时先隔离旧写入方，再提升后备实例，避免双向写入。
5. 在独立演示数据上注入应用、数据库、网络和整机故障，记录并验收 RPO/RTO。

分层进度（不要跨层宣称）：**同一停写窗口内的数据层迁移与切回已在演示数据上验收** —— 两侧内容级指纹逐项相等、隔离期间应用用户写不进去、切回后旧写入方可重新写入且目标侧保持冻结（见 [验证记录](validation.md#stateful-migration)）。仍然**没有**验收的是：真实 `sub2api` 容器参与、入口层流量切换、停写窗口之外的增量、自动故障转移。所以「能迁移演示数据」不等于「生产数据库可以故障切换」。

## 存储

无 RAID 的多磁盘冗余不能把同一 ESXi 宿主上的多个 VM 当作独立容灾域。Ceph 等系统只能在其 OSD、网络、仲裁、快照或复制策略完成配置并通过故障注入后才提供存储冗余；存储健康也不自动等于数据库事务一致。

`.52` 在重装 ESXi 前必须保持禁用。重装后先只读确认专用磁盘、硬件身份和共享故障域，再决定是否加入；既有未知文件系统不得因为“即将重装”而被自动格式化或接管。
